# decision-tests — лаборатория decision-моделей

Зачем это сделано
------------------

Decision-модели (System One) — класс, который не генерирует текст, а отвечает на
типизированные вопросы распределением вероятностей по вашим вариантам. Контракт
появился меньше месяца назад (см. [decision-models.md](decision-models.md)), а весь
класс держится на одном свойстве: **решение модели целиком определяется тем, что ты
ей положил** — формулировкой вопроса, набором вариантов ответа и состоянием (state).
Один висящий `\n` в стейте, один синоним в списке ответов, один лишний бинарный
вопрос — и «надёжный классификатор» начинает врать.

Проверить это на словах нельзя. Нужен инструмент, который меняет **одну переменную**
и показывает, **как сместились веса**. Это — попытка построить такой
инструмент в самой примитивной форме: YAML-спека → прогон → YAML-снимок.

Фактически это три инструмента, входящие в один и тот же каркас:

- **Отладка.** Правишь одну переменную (формулировку, набор вариантов, поле стейта) —
  прогоняешь — смотришь снимок. Никакой конфигурации, никаких bless-режимов и
  диффов с допусками: правка YAML + один запуск скрипта.
- **A/B.** Снимки лежат по моделям (`results/<model>.<source>`) и схлопываются в
  таблицу по паре `state`/`q`. Входы одинаковые, разница только в весах — честное
  сравнение моделей, версий моделей и формулировок.
- **«Файнтюнинг» без весов.** У decision-моделей веса заморожены, а поведение
  задаётся на уровне данных: criteria, описания вариантов, набор вопросов. Тест-файл —
  одновременно objective, eval set и regression-тест. Мы подкрутили поведение модели,
  не тронув ни одного веса: добавили вариант `venting` в `spam` — и голоса переехали.

И четвёртое, самое долговечное: **спеки — это самоподдерживающаяся документация и
список правил**. Правило «варианты должны быть разнонаправлены» живёт не в тексте
README, а в вопросе `resolution` с синонимами — и каждый прогон его перепроверяет.
Правило, которое может сломаться незамеченным, — не правило. Правило, которое падает
как тест, — правило. Все правила ниже всплыли из прогонов, ни одно не придумано
заранее.

Структура
---------

```
README.md               # этот файл
AGENTS.md               # инструкция для агента, работающего с лабораторией
decision_tests.py       # раннер (msgspec + PyYAML, без внешних SDK)
requirements.txt        # msgspec, PyYAML
decision-models.md      # ресеч класса: контракт API, лимиты, бенчмарки
test/*.yaml             # спеки тестов (вход)
results/<model>.<file>  # снимки ответов модели (выход)
```

Быстрый старт
-------------

```bash
# зависимости (один раз)
pip install -r requirements.txt

# прогон всех тестов из test/; нужен Ollama с decision-моделью
MODEL=<tag> python decision_tests.py

# ...или одного файла
MODEL=<tag> python decision_tests.py test/decision-tests.template.yaml
```

Раннер ходит в `POST $OLLAMA_HOST/v1/systemone` (дефолт `http://localhost:11434`).
Проверить, жив ли сервер и какие модели доступны: `curl -s $OLLAMA_HOST/v1/models`.
Модель задаётся только через env `$MODEL` — в YAML она не хранится, чтобы снимки
разных моделей были сопоставимы.

Формат теста
------------

```yaml
test:
  states:                 # строка ИЛИ JSON-объект с полями
    - Our checkout has returned HTTP 500 errors since 9am.
    - ticket:
        text: Our checkout has returned HTTP 500 errors since 9am.
        priority: critical
  questions:
    - name: team          # ключ в ответе модели
      q: |                # instructions
        Which team should handle this ticket?
      answers:            # criteria: ключ → описание
        billing: Payments and refunds
        bug: Software errors
        account: Login and account access

    - name: urgent        # да/нет — ключи обязательно в кавычках,
      q: |                # иначе YAML превратит их в bool и msgspec упадёт
        Does this ticket need attention within the hour?
      answers:
        "no": No urgency
        "yes": Needs attention within the hour
```

Типы вопросов:

| `type` | `answers` | Выход |
|---|---|---|
| `choice` (дефолт) | map ключ → описание, 2–26 вариантов | `choice` + `probabilities` + `confidence` |
| `noul` | map, 2–10 вариантов | `noul` (null / true / false) |
| `score` | упорядоченный список уровней от низшего к высшему | `score` + `confidence` |

Один вопрос к одному стейту — один запрос. Прогон = `число стейтов × число вопросов`.

Снимок
------

Снимок в `results/<имя_модели>.<имя_файла_теста>` хранит verbatim-ответ API
(`type/choice/probabilities/confidence/score/noul`), `source` — путь до файла теста,
числа округлены до 4 знаков. Вход и выход — **разные файлы**: их можно
склеить (`yaml.concat`) и отдать LLM для разбора.

Правила (выведены из прогонов)
------------------------------

1. **Варианты ответов — разнонаправленные**, без синонимических пар: синонимы делят
   массу и делают выбор недетерминированным (`resolution` с deny/decline/ask/clarify
   оставлен в спеке как негативный кейс).
2. **Порядок вариантов — скрытая переменная эксперимента.** Дубль одного вопроса с
   обратным порядком (`team` vs `team_rev`) на неоднозначных стейтах переворачивает
   выбор у всех моделей, Δp до 0.41 — больше, чем разница между моделями. Перед A/B
   порядок фиксируется.
3. **Бинарный вопрос на небинарную реальность врёт.** Пока в `spam` не появился
   вариант «злой, но легальный» (`venting`), модель сажала токсичные тикеты в `spam`
   с низким confidence.
4. **`state.strip()` обязателен:** висящий `\n` из YAML-блока `|` реально меняет ответ.
5. **State — первый класс данных.** JSON-объект с полем `priority: critical` поднимает
   `urgent` у всех моделей (0.49 → 0.92), хотя вопрос про это поле не спрашивает;
   убираешь поле — эффект обратим.
6. **Вопрос к несуществующему полю — тест на галлюцинации.** Одни модели честно
   отвечают «поля нет», другие выдумывают поле — но с низким confidence (0.09–0.18
   против 1.00 у настоящего ответа).
7. **`confidence = 1 − H(p)/ln(N)`** — нормализованная энтропия, а не вероятность
   правоты. Низкий confidence на спорном ответе — сигнал «модель не знает», и на
   практике он хорошо разделяет настоящие и выдуманные ответы.
8. **Ключи `"false"`/`"true"`/`"no"`/`"yes"` — только в кавычках**, иначе YAML даёт bool
   и msgspec падает на валидации.

Проверено на
------------

Python 3.14, msgspec + PyYAML; decision-модели (октябрь 2026, от меньших к
большим): `laya:322m-multilingual-bf16`, `d1-omni:600m`, `kev:0.8b-q8_0`,
`tev1:0.8b`, `d1:3b`, `tev1:4b`, `kev:4b-q8_0`, `kev:9b-q8_0`, `clef-flash:9b`,
`nimble:9b`, `nimble-v3:9b`. Снимки одного теста по разным моделям сравниваются по
паре `state`/`q` — одинаковые входы, разница только в весах.

Не пошла: `strands-decider:2b` — инференс требует MLX, которого в этом окружении
нет (Ollama отвечает 500 на любой запрос `/v1/systemone`), модель удалена из пула.
